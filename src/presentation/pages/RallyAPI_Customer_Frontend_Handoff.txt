1. Architecture Overview
RallyAPI is a food delivery platform (similar to Swiggy/Zomato) built as a .NET 8 Modular Monolith. The
backend is organized into independent modules, each with its own domain logic, database schema, and
API endpoints. As a frontend developer for the Customer app, you will primarily interact with endpoints
from the following modules:
Module
What It Gives You
DB Schema

All modules share a single PostgreSQL database (rallydb) but use separate schemas for isolation. The
API runs as a single process, so all endpoints share the same base URL. Communication between
modules happens via domain events (MediatR) internally — this is transparent to you as a frontend
consumer.

2. Authentication & Token Management
Customer authentication uses Phone + OTP verification. There is no email/password login for customers.
The flow produces two tokens: a short-lived JWT access token (15 min) for API authorization, and a
long-lived opaque refresh token (30 days) for seamless session renewal.

2.1 OTP Login Flow
The customer login is a 2-step process: request OTP, then verify OTP. If the phone number is new, the
user is automatically registered during verification (no separate signup endpoint needed).
Step 1: Request OTP
POST /api/customers/otp/send
Content-Type: application/json
{
  "phoneNumber": "+919876543210"
}
Response: 200 OK with a success message. The OTP is sent via SMS (in DEBUG mode it is logged to
console as 123456).
Step 2: Verify OTP
POST /api/customers/otp/verify
Content-Type: application/json
{
  "phoneNumber": "+919876543210",
  "otp": "123456"
}
Success Response (200):
{
  "accessToken": "eyJhbGciOiJSUzI1NiIs...",
  "refreshToken": "base64-encoded-random-string",
  "accessTokenExpiresAt": "2026-03-03T12:30:00Z"
}
NOTE: Phone numbers must include country code (e.g., +91 for India). The backend normalizes the number
by stripping spaces and dashes, keeping only digits and +.

2.2 Token Refresh Flow
When the access token expires (after 15 min), use the refresh token to get a new pair. The old refresh
token is automatically revoked (rotation). Your app should implement this as an interceptor/middleware
that retries failed 401 requests after refreshing.
POST /api/auth/refresh
Content-Type: application/json
{
  "refreshToken": "your-current-refresh-token"
}
Success Response (200):
{
  "accessToken": "new-jwt-token...",
  "refreshToken": "new-refresh-token",
  "accessTokenExpiresAt": "2026-03-03T12:45:00Z"
}
IMPORTANT: Theft Detection: If a revoked refresh token is reused (e.g., by an attacker who stole the old
token), the server revokes ALL sessions for that user. The legitimate user will be forced to re-login. This is
expected security behavior — always discard old refresh tokens immediately after rotation.

3.5 Pricing & Delivery Fee
Before placing an order, fetch a delivery fee quote. The pricing engine applies up to 7 dynamic rules (base
fee, distance, time surge, demand surge, weather surge, special day, 3PL delivery). The quote is valid for
10 minutes and includes a quoteId that must be passed when placing the order.
POST  /api/pricing/calculate
Calculate delivery fee for a restaurant-to-customer delivery.
Auth: Bearer Token (Customer)
Request Body
{
  "restaurantLatitude": 12.97159000,
  "restaurantLongitude": 77.59456000,
  "customerLatitude": 12.93423000,
  "customerLongitude": 77.61648000
}
Success Response (200)
{
  "quoteId": "uuid",
  "totalFee": 45.00,
  "currency": "INR",
  "breakdown": [
    { "rule": "BaseFee", "amount": 20.00 },
    { "rule": "DistanceFee", "amount": 15.00 },
    { "rule": "TimeSurge", "amount": 10.00 }
  ],
  "expiresAt": "2026-03-03T12:40:00Z"
}
NOTE: The quoteId expires after 10 minutes. If the user takes longer to checkout, fetch a new quote. Display
the breakdown to the user for transparency.

Recommended Error Handling Flow
1. On 401: Attempt token refresh via /api/auth/refresh. If refresh also fails with 401, redirect to login screen.
2. On 429: Show a user-friendly "Please wait" message. Implement exponential backoff for retries.
3. On 400: Parse the error message and display it to the user (e.g., "Restaurant is not accepting orders").
4. On 500: Show a generic error screen. Log the traceId for support escalation.
5. On network failure: Show an offline banner and retry with exponential backoff.

8. Rate Limiting
The API applies per-IP sliding window rate limits on authentication endpoints. The sliding window
algorithm prevents burst attacks at window boundaries.

Limit
Window
Response on Exceed

NOTE: Additionally, the OTP service has its own rate limiting: max 3 OTP requests per phone number per

UI when the user hits these limits.
Frontend UX for Rate Limits
When a user taps "Resend OTP", disable the button for 30-60 seconds with a countdown timer. This
prevents users from accidentally burning through the rate limit. If a 429 response is received, show a clear
message like "Too many attempts. Please try again in X minutes."

Quick Start Checklist
1. Ensure Docker is running with Redis (rally-redis) and PostgreSQL.
2. Run the API: dotnet run from the RallyAPI.Host project.
3. Send OTP to any +91 number using POST /api/customers/otp/send.
4. Verify with OTP 123456 to get your access and refresh tokens.
5. Use the access token in the Authorization header for all subsequent requests.
6. When you get a 401, call /api/auth/refresh with the refresh token.
7. Start building! Refer to this document for endpoint details and data shapes.
